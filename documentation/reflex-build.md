# Reflex Build

## Introduction

Reflex Build is a project-generation system centred on `reflex generate`.
It generates native build projects from declarative `project.cfg` files, rather
than requiring backend-specific project files to be authored by hand. A single
description can emit Visual Studio, Xcode, Android, Linux Makefiles, and CMake.

The CLI also provides convenience commands to clean generated output, run a
generated build, and open an IDE project. Persistent build variables provide
high-precedence configuration without editing cfg files, and the task API can
chain commands into reusable local workflows.

`project.cfg` is the declarative source description consumed by `reflex generate`.

The current format is `format: 1`. Normal projects include a shared file from
`project_configs/`, which declares the format and standard Reflex templates,
so leaf projects do not normally write `format` themselves.

## 1. Structural model

The format has a fixed hierarchy:

```text
Project
  |- Template
  |- Target
  |    `- Platform
  |         `- Configuration
  `- Library
       `- Platform
            `- Configuration
```

Structural entities use typed PropertySheet objects:

```propertysheet
include: "$[get_reflex_path:]/project_configs/cpp_app.cfg";

name: "Example";

@Target App:
{
	inherit: cpp_app;

	@windows:
	{
		@Configuration Debug: { optimization: none; };
	};
};
```

| Type | Name | Allowed parent | Meaning |
|---|---|---|---|
| `@Template` | Required | Project | Reusable, uninstantiated target definition |
| `@Target` | Required | Project | Product generated by native build tools |
| `@Library` | Required | Project | External static-library product |
| `@windows`, `@macos`, `@ios`, `@android`, `@linux` | None | Template, Target, Library | Platform driver |
| `@Configuration` | Required | Platform | Named build configuration |

Platforms have fixed names and must be anonymous. Disable an inherited object
explicitly:

```propertysheet
@ios: { enabled: false; };
```

### Templates and inheritance

`inherit` accepts a template name or an array:

```propertysheet
@Target Standalone: { inherit: [cpp_app, product]; };
```

Inheritance is copy-based and declaration ordered. A local template must be
declared before use; templates in included documents are already available.
Template lookup searches the current document first and then included documents
recursively in declaration order, returning the first matching ID. `inherit`
overwrites properties already present on the receiving object; properties
written afterward override the copied values. Later templates in an inheritance
array override earlier templates.

Matching platform and configuration objects merge by structural identity.
After inheritance, ordinary property lookup follows:

```text
Configuration -> Platform -> Target -> Project
```

The closest property masks the same property ID at every parent scope.

### Lists, appending arrays, and `@Unset`

Logical lists accept a scalar or an array and are stored as arrays. Most list
properties replace an inherited value when assigned. `dependencies` and build
phase arrays are the exceptions: their values append by default, including
across inherited scopes and repeated declarations.

```propertysheet
dependencies: ReflexCommonVm;
dependencies: [AcmeDSP, AcmeUI];

@BuildStep post_build:
{
	name: "Copy assets";
	command: ["copy-assets", "assets", "$(OutputName)"];
};
```

Use `@Unset <property>;` to clear a property at the current scope. It works
for scalar, map, and array properties. For an appending array, unset it before
the next declaration to discard inherited and previously accumulated values,
then add the replacement values:

```propertysheet
@Unset dependencies;
dependencies: [StandaloneRuntime, AcmeDSP];

@Unset post_build;
@BuildStep post_build: { name: "Package"; command: ["package-app"]; };
```

## 2. Includes and persistent variables

### Includes

`include` accepts one filename or an array. Relative paths are resolved from
the declaring file. Every included file remains a separate project document
with its own root, source path, templates, targets, and libraries. Documents are
acquired recursively before the including document, and include cycles are
errors.

```propertysheet
include: ["common.cfg", "products/app.cfg"];
```

Symbol lookup searches the current document first and then included documents
recursively in declaration order, returning the first match. This applies to
template inheritance and to target/library dependencies. A target retains the
document that declared it, so its relative paths and generated project folder
do not change when another project includes it.

Use forward slashes in authored paths. Other relative paths are resolved from
the folder of the document that declared the relevant target or library.

`import` is accepted as a compatibility spelling and adds documents to the same
ordered lookup graph after `include` entries. New files should use `include`.

### Persistent variables and `#if`

ReflexCLI has one persistent variable layer, shared by conditional selection,
include-path resolution, and project-variable expansion. Names are exact and
case-sensitive. A stored value is either a boolean or a string.

Manage the persistent values with:

```text
reflex set KEY true
reflex set KEY false
reflex set KEY value
reflex get KEY
reflex unset KEY
reflex variables
```

`set` stores `true` and `false` as booleans; every other value is a string.
`get` prints the value for one exact key, `unset` removes it, and `variables`
lists the persistent variable set.

Use `export` to write persistent variables and saved tasks as a PropertySheet.
Both `export` and `import` use `./export.cfg` by default; pass `--path` to use
another file. Export asks before replacing an existing file. Import merges the
file over the current saved state, replacing only variables and tasks with the
same names. Tasks are keyed by their exact task names, rather than stored as an
ordered list. Run `reflex reset` first when a complete replacement is wanted.

```text
reflex export
reflex export --path path/to/shared-state.cfg
reflex import
reflex import --path path/to/shared-state.cfg
```

Persistent variables are available to the PropertySheet preprocessor. Boolean
variables can be used directly, and string values have Key32 aliases for
comparisons:

```propertysheet
#if (reflex_source)
{
	@Target ReflexCommon: { inherit: reflex_target; };
}

#if (var == test)
{
	@Target Test: { inherit: test_target; };
}
```

Persistent values also form the highest-precedence variable overlay. They are
applied while resolving include paths and again when resolving each final
target's variables, so a CLI value overrides a cfg default at every scope.
Declare cfg defaults with `variables`:

```propertysheet
variables:
{
	APPLE_TEAM_ID: "";
};
```

For example, `reflex set APPLE_TEAM_ID ABSCFASDS` overrides the empty cfg
default. Project variables follow structural parent lookup and may reference
one another regardless of declaration order. Unknown variables and cycles are
errors.

| Built-in variable | Value |
|---|---|
| `$(Platform)` | `windows`, `macos`, `ios`, `android`, or `linux` |
| `$(Configuration)` | Active configuration name |
| `$(TargetName)` | Symbolic target name |
| `$(OutputName)` | Resolved product name |
| `$(Extension)` | Resolved extension |

`$(Architecture)` is deferred to the native build. On Apple platforms,
`$(PlatformVariant)` is also deferred and identifies the selected SDK variant.

Derived values use `$[function:input]`. Functions include `lowercase`, `strip`,
`package_identifier_segment`, `generate_4cc`, `path`, `constant`,
`get_reflex_path`, and `get_reflex_cli_path`.

## 3. Project and target reference

### Project properties

| Property | Description |
|---|---|
| `format` | Format version; currently `1` |
| `name` | Required for a document containing generated targets |
| `include` | Included project document or array |
| `import` | Compatibility spelling for `include` |
| `default_configuration` | Optional configuration key |
| anonymous `@Variables` | Project variable defaults |

Build platform support comes from each target's enabled platform objects.
Template-creation metadata is declared separately in the template's
`install.cfg`.

### Target properties

| Property | Description |
|---|---|
| `enabled` | Whether the structural object participates; default `true` |
| `inherit` | Template name or array |
| `type` | `console`, `app`, `dynamic_library`, or `static_library` |
| `output_name` | Product name; defaults to project name |
| `extension` | Optional extension without a leading dot |
| `output_directory` | Product output directory |
| `intermediate_directory` | Intermediate-object directory |
| `architectures` | Architecture key or array |
| `dependencies` | Symbolic target name or array |
| `cmake_identifier` | Optional public CMake target, for example `Reflex::Common` |

`@Target` objects are generated, while `@Library` objects describe externally
provided libraries and are linked without generating a build target.

### External libraries

`@Library` places an external static library in the symbolic dependency graph:

```propertysheet
@Library AcmeDSP:
{
	inherit: reflex_common;
	@windows: { path: "third_party/acme/$(Configuration)/AcmeDSP.lib"; };
	@macos: { path: "third_party/acme/$(Configuration)/libAcmeDSP.a"; };
};
```

`path` is the exact product path. If omitted, emitters use the symbolic name
and native toolchain conventions. `cmake_identifier` takes precedence in CMake
linkage and in Android Prefab consumption. Libraries never produce native
projects.

### Build settings

| Property | Values |
|---|---|
| `cpp_standard` | `cxx17` or `cxx20` |
| `rtti` | Boolean |
| `optimization` | `none`, `size`, `speed`, or `full` |
| `defines` | Named string map declared with `@Variables defines` |
| `include_directories`, `compiler_options` | String or array |
| `warning_level` | `none`, `relaxed`, `standard`, or `pedantic` |
| `floating_point` | `default`, `precise`, `fast`, or `strict` |
| `runtime_library` | `static` or `dynamic` |
| `debug_information`, `dead_strip` | Boolean |

Platform and configuration scopes may override these values. Emitters reject
variation where a native representation requires an invariant value.

Preprocessor definitions use variable-map syntax. An empty value emits the
name alone; a non-empty value emits `NAME=value`. Inherited maps merge by name,
and `@Unset defines;` clears the inherited definitions before a replacement:

```propertysheet
@Variables defines:
{
	FEATURE_ENABLED: "";
	PRODUCT_VERSION: "$(PRODUCT_VERSION)";
};
```

### Files

Use typed `@Files` blocks named `sources`, `headers`, or `other`:

```propertysheet
@Files sources:
{
	'': "$(REFLEX_PATH)/src/reflex_ext.cpp";
	code: ["code/entry.cpp", "code/app.cpp"];
};

@Files headers: { code: "code/**/*.h"; };
@Files other: { '': "resources.xml"; resources: "resources/**/*"; };
```

Values may be strings, arrays, or nested presentation groups. Supported
wildcards are `folder/*`, `folder/*.suffix`, `folder/**/*`, and
`folder/**/*.suffix`. Windows additionally supports `@Files resources` for
`.rc` and `.res` files.

### Build steps

```propertysheet
@BuildStep pre_build:
{
	name: "Build resources";
	command: ["$(REFLEX_CLI_PATH)", "build-resources", "--path", "resources.xml"];
	inputs: "resources.xml";
};
```

Use an object array for multiple actions. Supported phases are `post_generate`,
`pre_build`, and `post_build`. Members are `name`, `command`, `inputs`,
`outputs`, and `always_run`. Commands are argument vectors, not shell strings.
Build-step declarations append to inherited actions by default. Use
`@Unset pre_build;`, `@Unset post_build;`, or `@Unset post_generate;` before a
new declaration when that phase must be replaced instead.

## 4. Included projects and dependencies

`dependencies` is an appending array of symbolic targets. Resolution searches
the current document first and then included documents recursively, returning
the first matching `@Target` or `@Library` ID:

```propertysheet
include: ["../netx/project.cfg", "../dsp/project.cfg"];

@Target App: { dependencies: [Netx, DSP]; };
```

Documents are acquired once by resolved path. Include cycles, dependency
cycles, and incompatible platform/configuration/architecture combinations are
errors.

A dependency supplies native build ordering and its linker input. Static
libraries are followed transitively, so an application only names its direct
dependency:

```text
App -> Nuance -> FreestyleCommon -> Netx, DSP
```

Included source projects generate in their own normal project folders;
consumers reference those external projects rather than private copies.
`@Library` objects link without native project references.

## 5. Platform properties

### Windows

Windows supports `sdk` and `@Files resources`. Architectures are `x86` and
`x64`.

### macOS and iOS

Apple properties are `frameworks`, `arc`, `bundle_identifier`, `code_sign`,
`development_team`, `info_plist`, `entitlements`, `icon`, and
`deployment_target`. macOS also supports `exported_symbols` and
`build_all_architectures`; iOS supports `launch_screen`. Architectures are
`x64` and `arm64`.

### Android

Android properties are `sdk`, `min_sdk`, `sdk_path`, `package_id`,
`archive_name`, `native_app_glue`, `gradle_dependencies`, and `assets`.
Architectures are `x86`, `x64`, `arm32`, and `arm64`.

### Linux

Linux supports console applications and static libraries. A configuration uses
one `native` or `x64` architecture.

## 6. CMake output

Reflex supports two CMake project-management routes:

1. Use `project.cfg` as the source of truth and run `reflex generate cmake`.
2. Maintain `CMakeLists.txt` directly and use product-level helpers from
   `ReflexHelpers.cmake`, such as `reflex_add_app`, `reflex_add_vm_app`,
   `reflex_add_audio_plugin`, and `reflex_add_console_app`.

Both routes use lower-level semantic operations from `ReflexBuild.cmake`:

```text
                        ReflexBuild.cmake
                    semantic build primitives
                               ^
                  +------------+------------+
                  |                         |
        ReflexHelpers.cmake       generated CMakeLists.txt
       product-level helpers        project.cfg translation
                  ^
                  |
       hand-maintained CMakeLists.txt
```

`ReflexConfig.cmake` includes both CMake layers, so
`find_package(Reflex CONFIG REQUIRED)` makes them available. Generated CMake
uses ordinary commands for direct mappings and `ReflexBuild.cmake` operations
for semantic or platform-dependent settings. It does not call product helpers,
because that would reapply defaults over values already resolved from cfg.

CMake is an emitter, not a structural platform. Each cfg target is emitted
once. Shared values appear once; differences use CMake properties, generator
expressions, or `REFLEX_PLATFORM_WINDOWS`, `REFLEX_PLATFORM_MACOS`,
`REFLEX_PLATFORM_IOS`, and `REFLEX_PLATFORM_LINUX` conditions.

Generated `CMakeLists.txt` is disposable and identifies `project.cfg` as its
source of truth. Representable `pre_build` and `post_build` actions become
CMake build actions; `post_generate` remains part of `reflex generate`.

### CMake declarations

Declare package discovery and variables explicitly:

```propertysheet
@Variables cmake_find_packages:
{
	Reflex: "CONFIG REQUIRED";
	Threads: "REQUIRED";
};

@Variables cmake_variables:
{
	REFLEX_ROOT: "$(REFLEX_PATH)";
};

cmake_includes: "$(REFLEX_PATH)/cmake/ReflexBuild.cmake";
```

A parent may instead provide dependencies using `FetchContent`,
`add_subdirectory`, or a dependency provider. Generated and imported source
targets link symbolically. An `@Library` with `path` becomes an imported static
target; a pathless library is emitted by symbolic name for a package or native
linker to resolve. A source target with a distinct `cmake_identifier` keeps its
physical build-target name and publishes a CMake alias. For Android libraries,
a namespaced identifier such as `Reflex::Common` publishes Prefab package
`Reflex`, module `Common`, while the AAR filename remains controlled by
`archive_name`.

## 7. Helper commands

`generate` is the primary command. It reads `project.cfg` from the current
folder by default and emits every enabled native platform unless a platform is
specified:

```text
reflex generate
reflex generate windows
reflex generate --path path/to/project.cfg windows cmake
```

Use `clean` to run the generated cleanup helper for one or more platforms, or
for every generated platform when no platform is supplied:

```text
reflex clean
reflex clean windows macos
reflex clean windows --path path/to/project
```

Use `build` to run generated build helpers. Provide a platform and optionally
one configuration; omitting the configuration runs every generated
configuration for that platform:

```text
reflex build windows
reflex build windows Debug
reflex build macos Release --path path/to/project
```

Persistent variables set with `reflex set` are resolved during generation, so
they can provide build-specific cfg values without modifying the project file.
See [persistent variables](#persistent-variables-and-if).

Use `run` to execute a command directly. The first argument is the executable;
every following argument is passed to it unchanged:

```text
reflex run git status
reflex run "C:\Program Files\Tool\tool.exe" --input "file with spaces.txt"
```

`edit` opens a generated IDE project for a supported platform:

```text
reflex edit windows
reflex edit macos --path path/to/project
```

### Task API

The CLI can save a named task as a sequence of commands. Define a task with
`=`; use `+` to separate each command. The task remembers the current project
folder and runs every command there when invoked:

```text
reflex debug = generate windows + build windows Debug
reflex debug
```

Use `reflex tasks` to list saved tasks. Tasks are a convenient way to compose
generation, cleanup, and build operations into a repeatable workflow.

Imported tasks may declare names for positional arguments. Task directories and
command arguments support the same `$(variable)` and `$[function:value]`
expressions as project values:

```propertysheet
tasks:
{
	'build-product':
	{
		arguments: ["product"];
		@WString directory: "D:/devt/nsa/projects/Freestyle/$(product)/";
		commands:
		[
			"generate", "windows",
			"+",
			"build", "windows", "release",
			"+",
			"build-installer"
		];
	};
};
```

The positional and named forms are equivalent:

```text
reflex build-product nuance
reflex build-product --product nuance
```

Persistent variables provide the initial values, caller inputs override them,
and nested tasks inherit the resulting task variables. A nested task's own
inputs override inherited values. Use `$[path:value]` for arguments passed to
external tools when the path separators must match the host platform.
